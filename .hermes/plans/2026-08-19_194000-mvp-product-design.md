# Проектирование MVP «чтоунастамзавтра.рф»

**Статус:** черновик архитектуры MVP

**Цель MVP:** дать жителям Новокузнецка и Кемеровской области простой способ находить мероприятия, а организаторам — добавлять события через личный кабинет с обязательной модерацией.

**Основной пользовательский поток:**

```text
Посетитель открывает афишу
  → ищет или фильтрует события
  → открывает карточку
  → сохраняет событие в избранное

Организатор регистрируется
  → заполняет профиль
  → создаёт событие
  → событие получает статус «На модерации»
  → модератор одобряет или отклоняет
  → опубликованное событие появляется в афише
```

---

## 1. Принятые решения

### 1.1. Тип приложения

MVP — публичный каталог событий с кабинетами и модерацией. Это не социальная сеть, не билетный сервис и не рекламная платформа на первом этапе.

### 1.2. Рендеринг и frontend

Предварительный выбор: **Next.js**.

Причины:

- SEO для публичных страниц событий;
- удобная маршрутизация;
- возможность серверного рендеринга публичной афиши;
- единая структура для публичной части и кабинетов;
- хорошая работа с адаптивными интерфейсами.

React SPA остаётся допустимой альтернативой, если при создании репозитория окажется, что инфраструктура проще для Vite + React.

### 1.3. Backend

- Python 3.11.
- FastAPI.
- SQLAlchemy 2.x.
- Alembic.
- SQLite локально.
- PostgreSQL для production.
- JWT access/refresh tokens.
- bcrypt/современная библиотека password hashing.

### 1.4. Стратегия доступа

- публичные GET-запросы к опубликованным событиям доступны без входа;
- создание событий требует роли организатора;
- модерация требует роли модератора или администратора;
- операции с избранным требуют авторизации;
- проверка прав выполняется на backend, а не только в интерфейсе.

### 1.5. Что сознательно не входит в дизайн MVP

- платежи;
- премиум-тарифы;
- продажа билетов;
- OAuth-провайдеры;
- нейрогенерация;
- автопостинг;
- интеграция с фотосервисом;
- карты;
- рекомендации;
- сложная репутационная система.

## 3. Пользовательские сценарии

### Сценарий A. Поиск события без регистрации

1. Пользователь открывает `/`.
2. Видит ближайшие опубликованные события.
3. Вводит поисковый запрос или выбирает фильтры.
4. Переходит на `/events` или `/search`.
5. Открывает `/events/[slug]`.
6. Видит название, описание, дату, время, место, цену, возрастное ограничение и организатора.
7. При необходимости нажимает «В избранное» и получает предложение войти.

### Сценарий B. Регистрация посетителя

1. Пользователь открывает `/register`.
2. Вводит имя, Email и пароль.
3. Подтверждает согласие с офертой и обработкой персональных данных отдельными чекбоксами.
4. Получает локальную учётную запись.
5. После входа может использовать избранное и историю.

### Сценарий C. Регистрация организатора

1. Пользователь регистрирует обычный аккаунт.
2. В кабинете выбирает «Стать организатором».
3. Заполняет название, контактный телефон, ИНН и адрес.
4. Профиль получает статус `pending_verification`.
5. После подтверждения администратором пользователь получает возможность создавать события.

На первом MVP проверку ИНН не автоматизируем: сохраняем данные и оставляем ручное решение администратора.

### Сценарий D. Создание события

1. Организатор открывает `/organizer/events/new`.
2. Заполняет обязательные поля.
3. Система проверяет даты, цену, длину текста и обязательные поля.
4. Событие сохраняется со статусом `pending_moderation`.
5. Организатор видит статус и комментарий модератора при отклонении.
6. После одобрения событие становится доступным публично.

### Сценарий E. Модерация

1. Модератор открывает очередь событий.
2. Фильтрует события со статусом `pending_moderation`.
3. Просматривает все данные события.
4. Выбирает «Одобрить» или «Отклонить».
5. При отклонении вводит обязательную причину.
6. Система записывает действие в журнал модерации.

### Сценарий F. Жалоба

1. Авторизованный или анонимный пользователь открывает опубликованное событие.
2. Нажимает «Пожаловаться».
3. Выбирает причину и при необходимости оставляет комментарий.
4. Жалоба появляется в `/admin/complaints`.
5. В MVP событие не скрывается автоматически: автоматическое скрытие по количеству жалоб переносится на следующий этап после накопления статистики.

## 4. Роли и права

| Действие | Посетитель | Организатор | Модератор | Администратор |
|---|---:|---:|---:|---:|
| Просматривать опубликованные события | Да | Да | Да | Да |
| Искать и фильтровать | Да | Да | Да | Да |
| Добавлять в избранное | После входа | Да | Да | Да |
| Создавать событие | Нет | Да | Нет | Да |
| Редактировать своё событие | Нет | Да | Нет | Да |
| Видеть черновики своих событий | Нет | Да | Нет | Да |
| Модерировать события | Нет | Нет | Да | Да |
| Просматривать жалобы | Нет | Нет | Да | Да |
| Управлять категориями и районами | Нет | Нет | Нет | Да |
| Назначать роли | Нет | Нет | Нет | Да |
| Удалять пользователя | Нет | Нет | Нет | Да |

Все проверки должны дублироваться на backend. Скрытие кнопки во frontend не считается защитой.

## 5. Состояния и правила события

### 5.1. Жизненный цикл события

```text
draft
  → pending_moderation
  → published
  → archived

pending_moderation → rejected → draft
published → hidden_by_admin → published
```

### 5.2. Правила MVP

- Новое событие создаётся как `draft` или сразу отправляется на модерацию.
- В публичную выдачу попадают только события со статусом `published`.
- Редактирование опубликованного события возвращает его на модерацию, если изменены существенные поля.
- Событие с датой в прошлом автоматически не показывается в разделе будущих событий.
- Архивация может быть автоматической при открытии выдачи или выполнена фоновой задачей позже.
- Отклонение требует причины.
- Удаление события в MVP лучше заменить на мягкое скрытие и архивирование.

## 6. Сущности базы данных

### 6.1. `users`

- `id` UUID/整数ный primary key.
- `email` уникальный.
- `password_hash`.
- `full_name`.
- `phone` nullable.
- `role`: visitor, organizer, moderator, admin.
- `is_active`.
- `created_at`.
- `updated_at`.

### 6.2. `organizer_profiles`

- `id`.
- `user_id` unique FK → users.
- `organization_name`.
- `inn` nullable на этапе первичного заполнения.
- `phone`.
- `legal_address`.
- `actual_address`.
- `verification_status`: not_requested, pending, approved, rejected.
- `verification_comment`.
- `created_at`.
- `updated_at`.

### 6.3. `categories`

- `id`.
- `name`.
- `slug` unique.
- `is_active`.
- `sort_order`.

### 6.4. `districts`

- `id`.
- `name`.
- `slug` unique.
- `is_active`.

### 6.5. `events`

- `id`.
- `organizer_id` FK → organizer_profiles.
- `category_id` FK → categories.
- `district_id` nullable FK → districts.
- `title`.
- `slug` unique.
- `short_description`.
- `description`.
- `poster_url` nullable.
- `start_at`.
- `end_at` nullable.
- `timezone`.
- `venue_name`.
- `address`.
- `age_limit` nullable.
- `price_type`: free, paid, donation, unknown.
- `price_min` nullable.
- `price_max` nullable.
- `ticket_url` nullable, хранится как обычная ссылка без продажи билетов.
- `status`.
- `moderation_comment` nullable.
- `published_at` nullable.
- `created_at`.
- `updated_at`.

### 6.6. `favorites`

- `user_id` FK → users.
- `event_id` FK → events.
- `created_at`.
- Составной уникальный ключ: `user_id + event_id`.

### 6.7. `event_views`

- `id`.
- `user_id` nullable.
- `event_id`.
- `session_id` nullable.
- `created_at`.

### 6.8. `complaints`

- `id`.
- `event_id`.
- `user_id` nullable.
- `reason`.
- `comment` nullable.
- `status`: new, reviewing, resolved, rejected.
- `moderator_comment` nullable.
- `created_at`.
- `resolved_at` nullable.

### 6.9. `moderation_actions`

- `id`.
- `event_id`.
- `moderator_id` FK → users.
- `previous_status`.
- `new_status`.
- `comment` nullable.
- `created_at`.

### 6.10. `refresh_tokens`

- `id`.
- `user_id`.
- `token_hash`.
- `expires_at`.
- `revoked_at` nullable.
- `created_at`.

## 7. Индексы и поиск

На первом этапе добавить индексы:

- `events.status`;
- `events.start_at`;
- `events.category_id`;
- `events.district_id`;
- `events.organizer_id`;
- `events.slug`;
- `events.title`.

MVP-поиск можно реализовать через SQLAlchemy с `ILIKE` для SQLite и PostgreSQL. После появления достаточного объёма событий перейти на PostgreSQL `tsvector` или `pg_trgm`.

Не оптимизировать полнотекстовый поиск заранее.

## 10. Дизайн MVP

### Главная

Основной тип поверхности — **Explore**.

Композиция:

- компактная шапка с логотипом, поиском и входом;
- крупная, но не рекламная область поиска;
- фильтры категорий и даты;
- блок «Скоро»;
- основная лента карточек событий;
- компактный календарный блок или ссылка на полный календарь;
- понятные состояния «ничего не найдено» и «события скоро появятся».

### Карточка события

- постер или нейтральный placeholder;
- дата и время;
- название;
- место;
- категория;
- цена или «Бесплатно»;
- возрастное ограничение;
- кнопка избранного;
- визуальная иерархия без множества декоративных бейджей.

### Кабинеты

Кабинет организатора — поверхность **Operate**:

- список событий;
- явные статусы;
- основное действие «Добавить событие»;
- фильтр по статусам;
- сообщения модератора.

Админка — также **Operate/Monitor**:

- очередь модерации;
- быстрый просмотр события;
- однозначные действия «Одобрить» и «Отклонить»;
- журнал действий.

### Адаптивность

Три контрольных состояния:

- 375px — одна колонка, фильтры в выдвижной панели;
- 768px — две колонки и компактная боковая фильтрация;
- 1280px — широкая лента, календарь/фильтры рядом с каталогом.

Интерактивные элементы — не меньше 44px по высоте.

## 11. Проверка MVP

### Backend

- тесты регистрации и входа;
- тесты refresh/revoke токенов;
- тесты ролей и запрета чужих операций;
- тесты создания события;
- тесты переходов статусов;
- тесты поиска и фильтров;
- тесты избранного;
- тесты жалоб;
- тесты модерации;
- тесты валидации дат и цены.

### Frontend

- публичная навигация;
- поиск и фильтры;
- открытие карточки;
- вход и регистрация;
- создание события;
- отображение статуса модерации;
- добавление в избранное;
- адаптивность.

### Приёмочный сценарий

1. Создать пользователя.
2. Создать организатора.
3. Создать событие.
4. Убедиться, что оно не показывается публично до модерации.
5. Одобрить событие администратором.
6. Убедиться, что оно появилось в каталоге и календаре.
7. Найти его через фильтры.
8. Добавить в избранное.
9. Отклонить другое событие и проверить отображение причины организатору.

## 12. Открытые вопросы

1. Нужна ли загрузка собственного постера уже в MVP или достаточно URL/локального media storage?
2. Требуется ли подтверждение Email до создания события?
3. Должен ли организатор создаваться отдельной регистрацией или через заявку из обычного кабинета?
4. Какой набор категорий использовать на старте?
5. Какой справочник районов Новокузнецка использовать?
6. Нужен ли отдельный город Кемерово сразу или сначала только Новокузнецк?
7. Где будет храниться media-файл: локально на VDS, S3-совместимое хранилище или Яндекс Облако?
8. Нужен ли SSR/SEO для первой версии или допустим CSR-прототип?
9. Какой домен и схема deployment будут использоваться в тестовой среде?
